# Worker Contracts

Boundary: load only when dispatching setup, authoring, or run/report workers. Workers act from the
explicit packet plus this contract only; hidden chat context, runtime identity, prior runs, or broad skill
invocation wording grants no authority.

## Packet Requirements

Every worker packet must include:
- task goal, worker type, and this contract path;
- source materials to read, including approved test plan items, feature description, scouting notes,
  applicable category/evidence references, and the Run Contract when side effects are allowed;
- feature/head ref and commit under test, target/base ref recorded separately, and exact branch/worktree
  paths where work and proof commands must run;
- allowed write scope with concrete paths, ownership of shared files, and non-overlap boundaries;
- approved commands/checks, cwd, environment assumptions without secret values, expected outputs, and
  required artifacts;
- stop conditions, escalation route, and completion-report requirements.

If a required field is missing, ambiguous, or inconsistent with the approved plan or Run Contract, stop
and report rather than inferring permission.

## Universal Worker Boundaries

Workers must not create worktrees or branches, switch the root worktree, merge, push, tag, force, clean
up outside their packet, install unapproved dependencies, start unapproved services, write tracked
secrets, change product code, weaken/delete/skip planned tests to hide failures, or treat dashboards as
a replacement for the portable proof receipt. Workers may not widen their write scope because a file is
nearby, convenient, generated by a tool, or mentioned in hidden context.

Approved side effects are exact. A changed install command, package-manager scope, env-file path,
service port, persistence namespace, artifact directory, reset command, teardown command, or dashboard
output requires renewed approval before action. Secret values never go in tracked files, committed docs,
logs, screenshots/images, videos, proof receipts, or dashboards.

## Setup Worker

Setup workers prepare only approved shared test configuration and environment prerequisites. They may
install only dependencies named in the Run Contract and write only approved manifests, lockfiles,
configuration, generated files, or gitignored env/example files in their packet scope. They must record
configuration paths, dependency commands, state/seed/reset method, artifact directory, service/process
ownership, and teardown plan. Stop on missing approvals, failed installs or health checks, tracked secret
risk, unclear persistence scope, port conflicts, or teardown that cannot be bounded.

## Authoring Worker

Authoring workers write tests only for assigned non-overlapping plan items and paths. They follow
scouted project conventions or the approved minimal structure; they do not reorganize existing tests or
edit implementation files. Tests should prove the assigned surface and category evidence: success,
failure, invalid/default input, state boundaries, CLI/API/browser artifacts, or unsupported mobile scope
as applicable. If implementation defects make the planned assertion red, preserve the red test and
report evidence; do not make the test weaker to obtain green output.

## Run/Report Worker

Run/report workers execute only the approved plan commands against the integrated test branch/worktree
that contains delivered feature/head code plus authored tests/config. They collect command outputs,
runner reports, logs, fixtures, snapshots, generated outputs, traces, and browser videos plus
screenshots/images when browser/web acceptance scenarios apply. They write or refresh the portable proof
receipt with run ID, run-specific artifact directory, tested feature/head ref and commit SHA, target/base
metadata, plan-item to test/config mapping, category/purpose/surface, exact commands/cwd/exit codes,
environment summary without secrets, setup/reset and teardown results, artifact paths, and red-test
evidence with likely cause.

Success may be reported only when every approved plan item is green and every required artifact exists
for the same run ID and tested commit. Red items, missing artifacts, unsafe state, stale evidence,
missing credentials, unbounded teardown, or product-code defects require a blocker/red-test report and
safe rerun guidance.

## Completion Report

Worker reports include changed or inspected files, item-to-test-file or shared-config maps, exact
commands/checks and results, artifact paths, environment/setup/reset/teardown results, red-test evidence,
blockers, approvals used, non-authorized actions left untouched, and self-review for the worker scope.
